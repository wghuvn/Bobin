# Task 5.1.2 — калибровка статичной FPS-позы

База: `df90025` (Bobin Craft 2.7.7-clean, Fabric 1.20.1, Java 17).

Приоритет этой работы — неподвижная `idle`: две руки Minecraft действительно
удерживают один технический объект. Анимация, инерция и движение не должны
скрывать ошибки геометрии или хвата. После `/bobin_glb fp show` presenter
показывает именно эту позу, без автоматического `raise`.

Статичная сцена переработана в Blender и проверена на экспортированных GLB.
**Проверка в Minecraft остаётся незавершённой:** полная сборка и запуск клиента
останавливаются до компиляции из-за HTTP 403 при загрузке Fabric Loom 1.7.4.
Поэтому этот отчёт не объявляет игровой визуальный критерий готовности достигнутым.

Проверка не выявила причины менять существующий `FabricGlbRenderer` или расчёт
skinning в `RigFrame`. Преобразование Blender `(x, y, z)` → glTF/Minecraft
`(x, z, -y)` сохраняет handedness. Вершины получают `jointWorld * inverseBind`,
а renderer не применяет mesh transform к ним второй раз. Отдельная диагностическая
матрица mesh-local skinning включает `inverse(meshWorld)` по своему назначению.
Эти части архитектуры сохранены.

## Единый контракт захвата

`GripFrameConvention` задаёт ортонормальный фрейм с положительным determinant:

- origin — контактная точка, расположенная с зазором 1 мм от поверхности;
- локальная +Y — основное направление вдоль удерживаемой поверхности;
- локальная −Z — нормаль ладони внутрь поверхности, +Z — тыльная сторона;
- локальная X = Y × Z, поэтому X × Y = Z и determinant = +1;
- большой палец правой руки находится со стороны −X, левой — со стороны +X.

Отражение фрейма не используется для зеркального отображения руки. Валидатор
отвергает scale, shear, отрицательный determinant, неортогональные оси,
перспективные компоненты и нечисловые значения. Допуск покрывает обычную
погрешность float при экспорте; входные данные не нормализуются молча.

Независимые точки и направления в общей glTF/Minecraft-системе:

| Контакт | Origin, метры | +Y primary | Нормаль ладони | Сторона большого пальца |
|---|---|---|---|---|
| Правая рука, бок основной рукоятки | `(0.03225, -0.115, 0.055)` | `(0, 0, -1)` | `(-1, 0, 0)` | `(0, 1, 0)` |
| Левая рука, нижняя передняя опора | `(-0.015, -0.016, -0.34)` | `(1, 0, 0)` | `(0, 1, 0)` | `(0, 0, -1)` |

Частично направленная вверх левая ладонь здесь уместна: она поддерживает
переднюю часть снизу, а пальцы загибаются вокруг её боковой грани. Правая
ладонь обращена к боковой поверхности основной рукоятки. Универсального
поворота «обе ладони вниз» нет.

Цепочка привязки: `Object Root → Grip Socket → Hand Target → Hand Rig`.
Объектный socket задан от размеров поверхности ещё до создания рук.
Контактный Hand Target имеет собственный локальный offset относительно
кости кисти и не совпадает с центром запястья. Bone-parent offset учитывает
положение хвоста кости в Blender. При импорте socket transform применяется
один раз; Java не добавляет корректирующие повороты кистей или scale.

Для пустых Blender-узлов экспортёр меняет базис с обеих сторон:
`N = C × M × inverse(C)`, где `C(x,y,z) = (x,z,-y)`.
Семантические оси захвата должны быть столбцами `C × M`. Поэтому локальная
матрица socket в Blender-генерируемом sidecar содержит фиксированную конверсию
`C`: `N × C = C × M`. Это одна конверсия базиса для всех четырёх sockets,
не подобранный поворот отдельной кисти. Независимые golden-матрицы в Blender
строятся прямо как `C × matrix_world` и сравниваются с импортированными.

## Технический образец и геометрия рук

Новый образец состоит из семи отдельных полигональных деталей:

| Деталь | Размеры Blender X × Y × Z, метры |
|---|---|
| Продолговатый корпус | `0.10 × 0.69 × 0.09` |
| Задняя опора | `0.16 × 0.16 × 0.10` |
| Основная рукоятка | `0.0625 × 0.085 × 0.18` |
| Задняя перемычка рукоятки | `0.04 × 0.02 × 0.053` |
| Передняя опора | `0.10 × 0.19 × 0.035` |
| Маркер продольного направления | `0.02 × 0.07 × 0.015` |
| Боковой контрольный маркер | `0.015 × 0.04 × 0.025` |

Серо-бирюзовые панели и цветные маркеры предназначены для проверки эргономики.
У объекта нет игровых свойств. Фаски, UV, геометрия, bind-поза и движения
создаются в Blender и экспортируются в GLB. Единица Blender остаётся одним
метром / Minecraft-блоком; физические размеры не меняются ради одного кадра.

Сохранены 36 костей: плечо, предплечье, кисть и пять цепочек по три кости
на каждую руку. Основное сечение предплечья Steve — 4 × 4 пикселя модели,
Alex — 3 × 4; один пиксель равен 1/16 м. Кисти компактнее предплечий, пальцы
короткие и угловатые. Рукава остаются отдельной оболочкой.

Каждая основная рука имеет 240 вершин / 238 полигонов и замкнутую поверхность;
все 18 костей этой руки имеют веса. Каждый рукав содержит 120 вершин /
109 полигонов и один намеренно открытый манжет (20 граничных рёбер).
В экстремальных тестовых сгибах длины рёбер меняются в пределах 0,739–1,333
от bind: умеренная деформация присутствует, утверждения о жёсткой геометрии
при любых углах нет.

Steve и Alex имеют отдельные Blender/GLB-геометрии; вариант не получается
масштабированием в Java. Сохранены UV стандартного скина 64 × 64, отдельные
области рукавов и использование актуального пользовательского скина через
vanilla texture manager. Новых сторонних библиотек не требуется.

## Статичная калибровка и анимации

`show()` переводит presenter в режим `staticIdle=true`. Поза выбирается на
нулевом времени; изменение часов, движение и поворот игрока не меняют
относительное положение рук и объекта. Запрос включить инерцию не выводит
калибровку из неподвижного состояния. `fp status` показывает этот режим.

Только явная команда `fp anim …` покидает режим калибровки. Команда
`/bobin_glb fp static` снова возвращает неподвижную позу. Существующие клипы
`idle`, `inspect`, `raise`, `lower`, `move` сохраняются для отдельных проверок;
их прохождение не используется как доказательство правильности `idle`.

Предоставленный FPS-референс показывает переходную позу с отдельным магазином
в левой руке. Он используется для общей композиции, перспективы и блочного
стиля. Статичная поза удержания одного объекта двумя руками проверяется
отдельно; точное копирование положения левой кисти или процентных границ
из переходного кадра не является целью.

## Команды воспроизведения

```sh
blender -b --python scripts/armament/export_first_person_fixture.py
blender -b --python scripts/armament/export_first_person_fixture.py -- --variant slim
blender -b --python scripts/armament/render_grip_diagnostics.py
python3 scripts/verify_first_person_schema.py
python3 scripts/verify_armament_schemas.py
JAVA_TOOL_OPTIONS=-Xbatch ./gradlew -p tools/armament-glb-check test dependencyReport --offline --no-daemon
./gradlew build
./gradlew runGlbDebugClient
```

Для CPU-target нужны JDK 17 и разрешённые Maven Central зависимости.
`--offline` применим при наличии кеша; первая загрузка требует сети.
Полная сборка дополнительно требует доступных репозиториев Fabric проекта.

При доступном запуске клиента, в первом лице, со здоровым персонажем и пустыми
обеими руками:

```text
/bobin_glb fp show
/bobin_glb fp static
/bobin_glb fp status
```

Сначала оценить только `staticIdle=true`: обе кисти, стороны больших пальцев,
контакт с рукояткой/опорой, размеры предплечий, центральный обзор и ближнюю
плоскость камеры. Сравнивать кадры при одинаковых разрешении и FOV; отдельно
проверить Steve/Alex, пользовательские скины и независимое выключение рукавов.
Затем, после оценки статичного хвата, отдельно проверить:

```text
/bobin_glb fp anim idle
/bobin_glb fp anim inspect
/bobin_glb fp anim raise
/bobin_glb fp anim lower
/bobin_glb fp anim move
/bobin_glb fp static
```

Повторные F3+T и наблюдение `fpVariants/liveTextures` требуют настоящего клиента.
До такой проверки нельзя утверждать отсутствие утечек GPU или окончательную
визуальную готовность игрового кадра.

Серверная логика, NPC AI, гранаты, дроны, техника и другие действующие системы
не изменялись: [scope audit](task5-1-2/validation/scope-audit.json) сравнивает
хеши с исходным `df90025`. Новых зависимостей нет, `build.gradle` и опасные
правила удаления не менялись. [Полный перечень изменений](TASK5_1_2_CHANGES.txt)
включает исходники, Blender/GLB, sidecars, тесты и проверочные артефакты.
Переход к третьему лицу и NPC не выполняется.
